## Findings

### High

**H1. The OpenAI secondary-provider path sends the raw answer schema to strict `json_schema`, and nothing tests it.**
- **Where:** `Assets/Scripts/RoomscriptLlmClient.ts:21-24`; `Assets/Scripts/Engine/perf/AnswerSchema.ts:14-15`.
- **What's wrong:**
  - The Gemini path converts schemas through `geminiResponseSchema`. That conversion was added after Gemini rejected `uniqueItems` live.
  - The OpenAI path passes `request.schema` unchanged with `strict: true`. The per-call schema contains `uniqueItems`, `minLength` and `maxLength`.
  - To my knowledge, OpenAI's strict structured-output mode supports only a subset of JSON Schema keywords, and these were among the unsupported ones. **I have not verified this.** It is the same class of failure that already broke Gemini.
  - The client's catch block maps any non-429 and non-401 error to `LlmError("unavailable")` (lines 33-37). A schema rejection would therefore fall back silently to the line bank instead of failing loudly.
  - The handoff confirms that the OpenAI request path has never had a live round trip.
- **Evidence:**
  - No vitest coverage, because the file is a Lens component.
  - `tests/ai/provider-schema.test.ts` covers Gemini only.
- **Fix:**
  - Extract the pure request-shaping and error-mapping code (`toOpenAiRequest`, `toGeminiRequest`, `mapProviderError`) into `Engine/ai/`.
  - Add an `openAiStrictSchema()` converter, like the Gemini one, that strips the unsupported keywords. `LineValidator` still enforces them.
  - Unit-test both request shapes and the error regexes.
  - Run one recorded OpenAI round trip before relying on the fallback model.

### Medium

**M1. There is no true golden replay.**
- **Where:** `tests/game/reducer.test.ts:17-25`; `tests/player/terminal.test.ts:18`.
- **What's wrong:** Every replay check compares `replayGame(log)` with the state the same code just produced. That proves determinism, but not stability across code changes: a reducer change alters both sides equally and still passes. The terminal demo pins a few end values (75 minutes, layer 2, 3 objections), which acts as a partial guard.
- **Fix:** Commit a golden fixture, for example `tests/game/golden/hero-demo.actions.json` plus the expected `hashHex(canonicalJson(state))`. Assert both. Update it deliberately whenever rules change.

**M2. The `breathesIn` acceptance criterion is untested.**
- **Where:** `Engine/game/Reducer.ts:131`; `reducer.test.ts:98`.
- **Fix:** `s.act({type:"Suggest",...s.graph.envelope})`, then assert that `events.at(-1).type === "breathesIn"` and that no card was revealed.

**M3. The 1,000-player fuzz still runs synchronously, the same shape that caused the RPC timeout.**
- **Where:** `tests/fuzz/Players.test.ts:7-17`; `scripts/fuzz-players.ts:32-118`.
- **What's wrong:** The test blocks the worker for 14.2 s alone and 20.3 s in the full run. That is about a third of the roughly 60-second RPC window that the synchronous case fuzz exceeded (see the counterfactual). A runner 3× slower, such as a 2-vCPU CI machine or a laptop on battery, would reproduce the exit-1 failure.
- **Fix:** Apply the same generator plus `setImmediate` batching (`fuzzPlayersAsync`), with a sync/async equivalence test.

**M4. The 5,000-case fuzz dominates the suite and has thin timeout headroom.**
- **Where:** `tests/case-generation/FuzzCases.test.ts:3-11`.
- **What's wrong:**
  - The test takes 63–67 s of its 120 s timeout. That is 96% of the full suite's wall time.
  - Its thresholds (≥90% acceptance, ≤50 attempts) are loose compared with what was observed (100% acceptance, 1 attempt). A large regression, down to 90% acceptance or many retries, would still pass.
  - The fuzz never exercises the repair or retry loop. Only the mocked-Dealer test does.
- **Fix:**
  - Keep a roughly 200-seed smoke test in the default suite with tight thresholds (for example, all accepted and `maxAttempts` ≤ 2).
  - Move the 5,000-case run to a `fuzz:cases` script, or to an opt-in vitest project or environment flag used in nightly or CI runs.

**M5. Broken-variant assertions are permissive, and they hide misleading solver diagnostics.**
- **Where:** `tests/case/Solver.test.ts:54`; `Engine/case/Solver.ts:298`.
- **What's wrong:**
  - With `toContain(test.code)`, a variant passes even if the solver also reports unrelated codes. A scratch replay (`broken-codes.ts`) shows that 17 of 20 variants produce exactly their code.
  - The 3 `NOT_UNIQUE` variants also emit `ROUTES_LT_2`, `MIN_ROUTE_TOO_LONG` and `BEAT_BREAKS_SOLVABILITY`, even though that fixture has **zero beats**. Solver.ts:298 emits `BEAT_BREAKS_SOLVABILITY` with subject `"base"` whenever the base case is unsolvable.
  - The `RepairPlanner` and the D5 compiler consume these codes, so a non-unique case would be reported partly as a beat problem.
- **Fix:**
  - Assert the exact code set, or a declared primary code, for each variant.
  - Decide whether base-case unsolvability should be reported as `NOT_UNIQUE` only, and pin that decision.

**M6. The B8 "min route ≤60%" and "always terminates" properties are weaker than they look.**
- **Where:** `tests/fuzz/Players.test.ts:13`, `tests/content/hero.test.ts:13`, `scripts/fuzz-players.ts:26-31,37`.
- **What's wrong:**
  - The hero's minimum route is **0 case-minutes** because physical observations are free, so `≤ 0.6 × clock` can never fail.
  - No test asserts a lower bound, such as requiring at least one interrogation or objection to solve.
  - Termination is guaranteed only by a fairness policy that forces a charged action every eighth step. A real player can stall forever with free actions.
  - The handoff documents both points, but the tests encode them as passing properties rather than as known design gaps.
- **Fix:**
  - Add an explicit test that states the intended design: either "solvable without interrogation is acceptable" or a minimum such as `minRouteMinutes ≥ N`.
  - Add a reducer-level guarantee (or a test documenting its absence) that free actions eventually cost time.

**M7. No CI exists, and no gate runs the type-check.**
- **Where:** `.github/` is absent; there is no git remote; `Tooling/package.json:6-13` has no `typecheck` script.
- **What's wrong:**
  - Nothing runs automatically. `tsc` currently fails with 2 errors that nobody noticed, because `npm test` never type-checks.
  - The Lens compiler checks engine code but not `Tooling/tests` or `Tooling/scripts`.
- **Evidence:** This run.
- **Fix:**
  - Add `"typecheck": "tsc --noEmit -p ."`.
  - Add a workflow that runs `npm ci`, `npm run typecheck` and `npm test` on `ubuntu-latest` (and optionally `windows-latest`), on Node 22.
  - Run the slow fuzz on a schedule (see M4).
  - Portability looks fine: import casing is exact, the `"junction"` symlink type is ignored on POSIX, and only git and node are required.

**M8. `tsc` errors in a test.**
- **Where:** `tests/ai/pipeline.test.ts:35,38`.
- **What's wrong:** `vi.fn(() => pending.promise)` has an empty parameter tuple, so `complete.mock.calls[0][0]` is typed `[]`. The code works at runtime, but it is a type error.
- **Fix:** `vi.fn((_request: LlmRequest) => pending.promise)`, or `complete.mock.calls[0]![0] as LlmRequest`.
